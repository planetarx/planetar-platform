# Parity Matrix — Palantir AIP + Apollo

> Palantir-side claims corrected 2026-11-14 against the planetar-palantir research (2026-11-06); rows it did not cover are unchanged.

This slice covers two Palantir products that bracket the *top* and the *bottom* of the stack:

- **AIP (Artificial Intelligence Platform)** — LLM-grounded reasoning, agents, semantic/RAG search, and a guardrailed tool-use surface, all bound to the **Ontology**. In our model AIP's *runtime* side is mostly a **surface (P8) over the kinetic plane (P7)**, but AI FDE, Palantir MCP and AIP Evolve also change schema, code and pipelines, so a change-management plane matters too ([AI FDE](https://www.palantir.com/docs/foundry/ai-fde/overview/)). In Palantir, actions are the governed write path, but agents are not limited to proposing them: chatbot action tools can auto-run ([tools](https://www.palantir.com/docs/foundry/chatbot-studio/tools/)), Automate can apply without review ([Logic and Automate](https://www.palantir.com/docs/foundry/logic/aip-logic-integration-automate/)), and reverts are narrow (OSv2, submitter-only, last edit only — [reverts](https://www.palantir.com/docs/foundry/action-types/action-reverts/)). Containment is not "free" in Palantir either: row and column controls stop at the read and do not follow data into model output or action edits ([propagation](https://www.palantir.com/docs/foundry/security/access-control-propagation/)). In planetar, routing every agent write through P7→R3 (00 §3 principle 3) is a design choice that contains *writes*; reads, egress and change management still need their own controls. The new roles AIP introduces are **R7 vector** (embeddings/RAG) and a **LLM gateway** (a P8/P2 component, not a storage role) — everything else (objects, links, actions, audit) reuses the existing ontology spine.
- **Apollo** — Palantir's continuous-delivery / fleet-management control plane: software is defined by Product plus Release Channel rather than a pinned version, so there is no single target state; Plans, polled by an agent in each environment, roll it forward under constraints, with recalls defaulting to roll-forward and downgrade opt-in ([overview](https://www.palantir.com/docs/apollo/core/overview/), [roll-off](https://www.palantir.com/docs/apollo/recalling-releases/roll-off-strategies/)), including into air-gapped environments. In our model Apollo is **pure P0 control**: it is the runtime that *executes the manifest* (13) across a fleet, plus the registry/versioning (**R10**) and audit (**R11**) that make releases governed and reversible. We have the manifest+compiler design (the thing Apollo would deliver) but **not the fleet-delivery runtime** — Apollo-class deploy is explicitly **deferred** in the inventory.

**Headline parity story.** AIP parity is *high on the semantics, deliberately thin on the model weights*: we own the containment (kinetic), grounding (ontology + R7), and audit story end-to-end and already have the Object API/Action executor an agent would call — we wire in an OSS LLM gateway and pgvector rather than train models. Apollo parity is *designed, not built*: the client manifest is closer to Apollo's Environment settings than to its release unit, a versioned Product Release ([products](https://www.palantir.com/docs/apollo/core/products-releases-versions/)), and the multi-environment delivery/recall runtime is a P0 component we have specified (manifest compiler + binder, 12 §4) without the fleet orchestration around it.

Role IDs (R1..R14) and plane IDs (P0..P8) are exactly as defined in [`10-STORAGE-ROLES.md`](../10-STORAGE-ROLES.md) and [`00-ARCHITECTURE-OVERVIEW.md`](../00-ARCHITECTURE-OVERVIEW.md). **Required** roles are **bold**; *enhancing* roles are *italic*.

## Notable gaps

- **No LLM gateway component** (Palantir's nearest analogue is its provider-compatible proxy endpoints). Every AIP retrieval/agent/chat row needs a model-call boundary (P8/P2) that meters, logs (R11), and gates (R13) — this is OSS-to-wire (a gateway in front of an external model), but nothing exists yet. It is the single highest-leverage missing piece for AIP parity.
- **Vector role (R7) is designed-only.** RAG, semantic search, and embedding re-ID all require **R7**; the port is specified ([`10` R7], [`12` §3 `VectorStore`]) but no embedding pipeline or `pgvector` adapter is built — so AIP grounding is currently keyword-only via doibio's Elasticsearch.
- **Apollo-class delivery runtime is deferred.** The manifest is the nearest analogue to Apollo's Environment settings (not its release unit) and the compiler/binder are specified (12 §4), but the multi-environment rollout/recall/air-gapped-delivery orchestration (channels, constraints, recalls, delta bundles) (the actual "Apollo") is not built; `temporal` (R14) is named as the OSS rollout engine but unwired.
- **Markings + propagating security are built in the platform core (2026-10-06) but not in the live service, and no AI-action gate uses them.** The AIP guardrail gate and Apollo multi-tenant isolation rows lean on **R13** (OPA PDP, unbound) + **R12** propagation (`spine/governed.ts`, `spine/system.ts`); `doibio` has **no FLS/row-level sharing**. Note the Palantir limit too: discretionary controls do not propagate into model output ([propagation](https://www.palantir.com/docs/foundry/security/access-control-propagation/)).
- **Multi-tenancy hardening** (inventory GAP) blocks true Apollo-style fleet isolation: per-client manifests give *architectural* separation, but runtime tenant isolation/quotas are unbuilt.
- **Agent loop + human-in-the-loop approval queue** are unbuilt: the Action executor can *commit* an agent's proposal, but there's no planner, tool-schema exporter, or **R14** approval inbox to drive propose-then-approve.
- **No eval/observability harness.** Eval-suite scoring (R9; AIP Evals has no built-in groundedness metric either) and AI-claim lineage (R12 via marquez) are unbuilt — a parity-credibility gap if AIP is demoed on real decisions.
