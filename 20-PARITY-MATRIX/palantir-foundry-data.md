# 20 — Parity Matrix · Palantir Foundry — Data Connection, Pipelines, Modeling

This slice maps Foundry's **data-engineering surface** — the part of Foundry that gets bytes *in* (Data Connection), *transformed* (Pipeline Builder / Transforms / Code Repositories), and *shaped* into the semantic layer (Datasets, Schemas, Object/Link/Action modeling, the Ontology Manager) — onto Planetar's planes ([`00`](../00-ARCHITECTURE-OVERVIEW.md)), storage roles ([`10`](../10-STORAGE-ROLES.md)), and the spine-vs-OSS split.

> Palantir-side claims corrected 2026-11-14 against the planetar-palantir research (2026-11-06); rows it did not cover are unchanged.

**Headline parity story.** Foundry's data plane is "land raw → record every write as a file-level transaction (`SNAPSHOT`, `APPEND`, `UPDATE`, `DELETE`) on a dataset branch → transform as jobs in one build system that records lineage → project into the Ontology" ([datasets](https://www.palantir.com/docs/foundry/data-integration/datasets/), [builds](https://www.palantir.com/docs/foundry/data-integration/builds/)). It is a file-transaction catalog with a job scheduler, with a streaming substrate (Flink over a hot buffer that archives to dataset files) alongside ([streams](https://www.palantir.com/docs/foundry/data-integration/streams/)); a bus-like log plus projections is an analogy, not the same model. Planetar's spine *has a similar shape*: the **bus is the spine of record** (an ordered, WAL-durable envelope on R3 plays the role a dataset transaction plays, though at message rather than file granularity), the **canonical model + registry** are the dataset/schema SSOT (R1+R10), **lineage propagates by construction** (R12, per-field `_provenance` already in doibio + ontology), and the **ontology service is the modeling layer** (object/link/action types with an OSDK-equivalent Object API, built). So the modeling and streaming-ingestion columns are largely *built spine* — what Planetar buys from OSS is the **connector breadth** (Airbyte/Singer in place of Foundry's Data Connection connectors; its docs nav listed 213 connector slugs on 2026-11-06, generic entries included, so the count is an upper bound — [core concepts](https://www.palantir.com/docs/foundry/data-connection/core-concepts/)), the **batch transform engine** (dbt/Spark replacing Foundry Transforms at volume), the **analytics scan layer** (clickhouse/duckdb for Contour-style preview), and **declarative no-code pipeline authoring** (the one genuine gap: there is no Pipeline-Builder GUI). Foundry is not coupled to one proprietary store: dataset files are open formats under a Hadoop FileSystem base directory, it implements the Iceberg REST Catalog with bring-your-own-bucket options, and virtual tables point at external storage with compute pushdown ([iceberg storage](https://www.palantir.com/docs/foundry/iceberg/storage/), [virtual tables](https://www.palantir.com/docs/foundry/data-integration/virtual-tables/)). Planetar's difference is narrower: it keeps the same logical model over a per-client engine mix behind role ports — sqlite+broker at the maritime edge, postgres+kafka+clickhouse in the cloud — with **zero application-code change** (see [`13`](../13-CLIENT-MANIFEST.md)).

> Status legend: **built** (a named repo does it) · **partial** (a named repo does part) · **designed** (specified, not coded) · **planned** (acknowledged, unspecified). Role IDs and plane IDs are verbatim from the spine. **Required** roles bold, *enhancing* roles italic.

## Data Connection

Getting external bytes to the edge and onto the bus as envelopes. Foundry's value here is connector breadth + virtual (query-in-place) tables, with a Source (config and credentials), a worker (where compute runs) and an egress policy (network path) kept separate ([architecture](https://www.palantir.com/docs/foundry/data-connection/architecture/)); Planetar owns the envelope/detector edge and wires OSS connectors behind it.

|---|---|---|---|---|---|

## Pipelines (Transforms · Builds · Scheduling)

Foundry's transform layer: Code Repositories (Python, Java and SQL, on single-node engines such as Polars by default for Python, with Spark beyond single-node capacity — [engines](https://www.palantir.com/docs/foundry/transforms-python/compute-engines/); streaming needs Java or Pipeline Builder — [stream vs batch](https://www.palantir.com/docs/foundry/building-pipelines/stream-vs-batch/)), Pipeline Builder (no-code; DataFusion-backed "faster" pipelines became the default in an announcement dated 2026-11-03), dataset transactions/branches, build schedules, and incremental/streaming transforms. Planetar reframes a "pipeline" as **a chain of projection consumers on the bus**, each step itself an event with lineage — but leans on OSS for the heavy SQL/Spark batch engine and has a real GUI gap.

| Feature | What it does (1 line) | Owning plane(s) | Required (bold) + enhancing (italic) roles | Spine vs OSS component | Status + backing path |
|---|---|---|---|---|---|
| Dataset = versioned file-level transactions | Each write is a `SNAPSHOT`, `APPEND`, `UPDATE` or `DELETE` transaction over files; a view replays from the latest `SNAPSHOT`, and `UPDATE` can overwrite files in a view ([datasets](https://www.palantir.com/docs/foundry/data-integration/datasets/)). The WAL-envelope mapping is an analogy at different granularity | P3, P4 | **R3**, **R1** | **Spine: the bus is the spine of record** — each dataset transaction is an ordered WAL envelope; R1 is a rebuildable projection | built — `planetar-broker` WAL+CRC32 gives ordered immutable log; projection model proven in ontology SQLite store |
| Schema / dataset registry | Declared schema per dataset, versioned (SemVer), codegen targets | P4, P0 | **R10**, *R1* | **Spine: canonical model + registry codegen** (R10 = git-vault SSOT) | built (slice) — `planetar-registry` codegen `~/github/planetarx/planetar-registry`; canonical model `~/data/vaults/docs/ARCH-canonical-data-model.md` |
| Batch transform (SQL/Python over datasets) | Author code that derives a dataset from upstream datasets | P4 | **R9**, **R1**, *R3* | Spine: transform output re-enters as envelopes; **OSS: dbt / Spark / duckdb** for the engine | designed — projection-consumer pattern built; general batch SQL/Spark transform engine not wired |

## Modeling (Datasets → Ontology: Object · Link · Action · Schema)

Foundry's Ontology Manager: define object types, link types, action types, interfaces, and the OSDK that apps consume. This is where Planetar is **strongest** — the ontology service is built, with an Object API that is OSDK-equivalent, kinetic Action Types as the sole write path, and identity resolution as the moat. Datasets become ontology objects via the resolution plane.

## Notable gaps

- **No no-code Pipeline Builder (visual DAG authoring).** The single clearest Foundry capability with no Planetar analogue — transforms are projection-consumer code, not drag-and-drop. Closest OSS path is dbt-as-code; a GUI is unbudgeted.
- **No general batch transform engine wired.** Streaming transforms (bus projection consumers) are built; SQL/Spark batch-over-datasets needs an OSS engine (dbt/Spark/duckdb) behind R9 — designed only.
- **Connector breadth is deferred (brief GAPS).** Foundry's Data Connection connectors (213 docs-nav slugs on 2026-11-06, an upper bound) map to Airbyte/Singer behind the R3/R6 edge, but only the 4 domain detectors + CSV import + webhooks are actually built; generic file/JDBC/agent connectors are designed/planned.
- **Lineage store binding is designed-only.** Per-field `_provenance` is built (doibio + ontology), but cross-dataset OpenLineage/Marquez (R12) for full pipeline lineage is not yet bound.
- **Markings + propagating security is built in the platform core (2026-10-06), not in the live service.** Marking propagation and FLS run in `spine/governed.ts` (`npm run governance` 70/70 on 2026-11-15); restricted views (row-limiting), per-record sharing and governed declassification are not built, and the live ontology and doibio have neither markings nor FLS.
- **Federated / virtual tables not coded.** Query-in-place (bigquery/snowflake/databricks behind R9) is specified but has no adapter.
- **Build scheduling / orchestration service absent.** R14 work-queue contract is specified (postgres SKIP LOCKED / Temporal); no scheduler runs builds yet.
- **Branching/scenarios (datasets and ontology) share one unimplemented mechanism.** Copy-on-write overlay on the canonical store is designed for both Foundry sandboxes and Ontology branches but not built.
- **RF lane is registered with no service**, and the **agent-based on-prem connector runtime** is planned, not designed.
