# 20 — Parity Matrix · Salesforce Platform — Automation, Security, DevOps

This slice maps the Salesforce **Platform** core — the configuration-not-code substrate that makes Salesforce a *platform* rather than a CRM app: **process automation** (Flow, Approvals, Apex async, Platform Events), **security** (profiles/permission-sets, OWD/sharing/FLS, Shield encryption + Event Monitoring), and **DevOps/ALM** (Metadata API, sandboxes, packaging, scratch orgs, change sets, Salesforce DX). For each feature we decompose into the eight planes ([`00`](../00-ARCHITECTURE-OVERVIEW.md)) and the fourteen storage roles ([`10`](../10-STORAGE-ROLES.md)), name the concrete spine capability or OSS engine that fills it ([`12`](../12-ADAPTER-CONTRACT.md)), and assign a conservative status against the built inventory.

**Headline parity story.** Salesforce's automation, security, and DevOps are all *metadata-driven* — declarative artifacts compiled and enforced by a runtime. That is structurally identical to our spine's bet: the **registry (R10)** is the SSOT for every definition; the **kinetic layer (P7)** is the only write path, giving validation/audit/reversibility for free (Flow ≈ chained Action Types); **governance (P1)** is defined once and propagates along **lineage (R12)**; and the **manifest (P0)** *is* the org's metadata + deployment topology. The spine already owns the hard, custom centre — Action Types, the registry+codegen toolchain, an immutable event-log audit, identity/principals — so most of this slice is either **already covered by a spine capability** or a thin adapter over a mature OSS engine (**Temporal** for long-running orchestration, **Keycloak**+**OPA** for identity/policy, **OPA** for the propagating-security PEP/PDP, **OpenSearch/ClickHouse** for the audit/SIEM sink, **Marquez** for lineage). The honest gaps are the *enterprise-hardening* pieces Salesforce has spent 20 years on: a visual declarative flow designer surface, field-/row-level sharing enforcement at breadth, platform encryption, and a true package-promote ALM pipeline — all **designed** here, not yet **built**.

> Role IDs **R1–R14** and plane IDs **P0–P8** are used exactly as defined in the spine. Required roles in **bold**, enhancing roles in *italic*. Status ∈ {built · donor · partial · designed · planned}; built/partial cite a repo path.

## Notable gaps

- **No declarative Flow *designer* surface.** The execution substrate exists (Action Types in `planetar-ontology/src/actions/executor.ts`), but the visual builder that lets a non-developer author flows is designed-only — the highest-leverage P8 gap for Salesforce parity. Long-running orchestration depends on a **Temporal** adapter behind the R14 `WorkQueue` port that is specified (`12 §3`) but not built.
- **Field-/row-level security is the biggest honest hole.** doibio has **no FLS and no row-level sharing**; markings + propagating security are designed-only across the whole platform (`11 §2`). Until the R12-lineage propagation and the R13/OPA PEP-at-adapter enforcement are built, OWD/sharing-rules/FLS/restriction-rules are all unenforced. This is the roadmap's named "propagating security — next" piece.
- **Shield-grade encryption and key custody are barely scoped.** Vault is named for secrets (`00 §2 P0`) but field-level encryption-at-rest with BYOK has no detailed mapping; status **planned**.
- **Identity/policy engines are present but not wired.** A Keycloak realm exists (`~/data/dev/doibio/keycloak/realm-export.json`) and OPA is the chosen R13 PDP, but no OPA policy bundle is authored and Keycloak is not yet behind the R13 adapter — so SSO/permission-sets/ABAC remain designed.
- **ALM is source-driven but not a promote pipeline.** R10 is git-backed (real, built) and a manifest-diff *is* a change set (`13 §3`), but scratch-org auto-provisioning, copy-on-write sandboxes/branching, package promotion, and Apollo-class fleet rollout are not built (the last is explicitly deferred).
- **Audit is built but not exported.** The immutable event-log (doibio) and broker WAL give a true append-only audit, but the ClickHouse/kafka SIEM sink and breadth read-auditing (Event Monitoring) are designed-only.
- **Decisioning (Einstein Next Best Action) is unstarted** — it needs the R9 analytics engine (ClickHouse) plus an LLM/model gateway, neither of which is in this slice's built set.
